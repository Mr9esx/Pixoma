# 工作流（Case）编辑器：可视化交互设计 + 输出绑定接线

## 1. 背景与问题

管理后台的 Case 编辑页现在把内部数据结构原样铺给用户：

- 「输入字段 / 输出字段 / 输入绑定 / 输出绑定」四个表格，手填 `key`、`node_id`、`field_path`、`index`；
- 「Workflow JSON / Input schema JSON」两个原始 JSON 文本框；
- 用户必须理解 `bindings`、`input_schema`、ComfyUI API 图这些内部概念才能配置一个工作流。

另外 `bindings.outputs`（输出绑定）目前运行时完全没有被消费：执行器把 ComfyUI 返回的所有图片收回来，机器人只发第一张。输出字段 / 输出绑定在端到端链路里是摆设。

## 2. 目标与边界

**目标：**

- 不熟悉 ComfyUI、不懂 JSON 的人也能把工作流配明白；
- 输入 / 输出字段可视化配置，`bindings` 与 `input_schema` 由表单自动生成，用户全程不碰内部结构；
- 输出绑定真正接到运行时：用户配了几个输出，执行后就按配置取回几个产物，顺序可控；
- 保留一个默认只读的「高级模式」逃生口，二次确认后才可手改原始数据。

**非目标：**

- 不做画布式节点编辑器：不重画 workflow 拓扑、不做拖拽连线，只做「字段 ↔ 节点参数」映射；
- 不做导入后自动猜输入 / 输出（导入只识别，配置仍由人完成；自动推断列为后续增强）；
- 不做 UI 格式 → API 格式转换的「完整无损」高级语义：覆盖常见 ComfyUI 导出即可，转换不了的给可读错误；
- 不改价格 / 菜单 / 分类 / 启用等其它编辑区（保留现有 Basics）；
- 不做扣费 / 余额校验。

## 3. 已确认决定

| 项 | 选择 |
|---|---|
| 页面布局 | 步骤式表单：一列三步（导入 → 用户输入 → 用户输出），底部只读预览 + 保存；新建按钮在右上角 |
| 导入方式 | 拖拽 / 选择文件 / 粘贴 JSON → 自动校验 → 显示「已识别 N 个节点」 |
| 未导入状态 | 步骤 2/3 整体置灰，提示「先导入工作流」 |
| 输入字段卡片 | 字段名 + 类型 + 来自节点（下拉，带中文说明）+ 参数（选完节点后出现）+ 必填 + 说明 |
| 输出字段卡片 | 字段名 + 类型 + 来自节点 + 输出序号（单输出自动选好且不显示） |
| 节点选择 | 下拉列表；内置常见节点中文别名表，未知节点显示原始类名 |
| 参数类型 | 由启发式规则推断，可手动改 |
| 高级模式 | 右上角小入口；默认只读；编辑需二次确认；普通用户不可见 |
| 预览 | 自动生成的 `bindings` + `input_schema`，只读、可折叠 |
| 保存校验 | 字段名唯一；必填输入必须已选节点和参数；至少一个输出 |
| 运行时 | 按输出绑定从 ComfyUI 结果中提取产物，无绑定的旧数据回退「全部收集」 |

## 4. 交互设计

### 4.1 页面结构

```
┌────────────────────────────────────────────────┐
│ 工作流名称 …… [● 启用]              [保存]      │  ← 顶栏
├────────────────────────────────────────────────┤
│ ① 导入工作流                                     │
│    [拖拽 JSON / 选择文件 / 粘贴]                 │
│    ✓ 校验通过：已识别 12 个节点 · 3 个可调输入    │
├────────────────────────────────────────────────┤
│ ② 用户需要提供什么                               │
│    [字段卡 1][字段卡 2] [+ 添加一个输入]          │
├────────────────────────────────────────────────┤
│ ③ 用户会得到什么                                 │
│    [字段卡 1] [+ 添加一个输出]                    │
├────────────────────────────────────────────────┤
│ 预览（自动生成，只读）▾                          │
│ 取消                    [保存工作流]             │
└────────────────────────────────────────────────┘
```

### 4.2 导入与校验状态

- **未导入**：步骤 2/3 置灰，只显示「先导入工作流，这里才会开放」；避免用户填了字段却绑不上节点。
- **校验中 / 校验通过**：通过后显示绿色横幅「已识别 N 个节点 · M 个可调输入 · K 个输出」和「重新导入」。
- **校验失败**：一句人话 + 常见原因清单（不是 JSON / 不是 ComfyUI 导出 / 结构损坏），不把 JSON 解析报错甩给用户；失败不影响已保存内容。
- 支持 ComfyUI API 格式（`{"1":{"class_type":…,"inputs":{…}}}`）与画布 UI 格式（`nodes[]` 数组）；UI 格式导入时自动转换为可执行 API 格式。

### 4.3 输入字段卡片

每张卡片：

- 字段名（用户会被问到的名字，如「参考图」）；
- 类型：文本 / 图片 / 数字 / 布尔 / 枚举（默认按所选节点参数推断，可手改）；
- 来自节点：下拉，显示「类名（中文说明）」，如 `Load Image（加载图片）`；支持搜索；
- 参数：选完节点后自动列出该节点可编辑参数；
- 必填开关、说明文字。

卡片下方固定提示：「节点和参数是从导入的工作流自动读出来的，不需要手填任何 ID」。

### 4.4 输出字段卡片

- 字段名、类型（图片 / 文本 / 文件）；
- 来自节点：下拉；
- 输出序号：仅当节点有多个输出时显示；单个输出自动选好。

### 4.5 高级模式

- 右上角小入口（视觉弱化）；
- 展开后显示自动生成的原始数据（`bindings` / `input_schema`），只读；
- 「进入编辑」需二次确认（防误改），编辑态标注「手动修改后，表单重新保存会覆盖此处」。

## 5. 数据与自动生成规则

### 5.1 导入解析

纯前端函数 `parseWorkflow(raw)`：

- 输入为 API 格式时直接解析；
- 输入为 UI 格式时按 `nodes[]` 重建：`id → {class_type: type, inputs: 由 inputs 连接与 widgets_values 重建}`；
- 输出 `WorkflowGraph`：`节点清单[{id, class_type, inputs:[{name, kind}], outputCount}]` + 可提交的 `bindings.workflow`；`outputCount` 由内置节点定义表推断，未知节点默认按 1 个输出处理（用户仍可手动配置序号）；
- 解析失败返回结构化错误（定位到节点，如「第 3 个节点缺少类型信息」）。

### 5.2 bindings 生成

由字段卡片实时推导，保存时才写入：

- `bindings.inputs[i] = {key, node_id, field_path}`；
- `bindings.outputs[i] = {key, node_id, index}`（单输出节点 `index = 0`）。

### 5.3 input_schema 生成

由输入字段列表推导，用户无感知：

- `type: "object"`，`properties` 按字段 key 生成：文本 → `string`、数字 → `number`、布尔 → `boolean`、枚举 → `string + enum`；
- `required` 为必填字段 key 列表；
- 图片 / 视频继续由现有媒体钩子校验（MIME / Blob），不重复进 schema。

### 5.4 保存校验

- **前端**：字段名唯一；必填输入已选节点 + 参数；至少一个输出；出错时在对应卡片标红并阻止保存。
- **后端增强**（`catalog/infrastructure/validation`）：`workflow` 图结构合法（每个节点有 `class_type` 且 `inputs` 为对象）；每条输入绑定引用的 `node_id` 与 `field_path` 存在于图中；每条输出绑定引用的 `node_id` 存在且 `index >= 0`。前端可能绕过的错误在这里兜底。

## 6. 运行时改动：输出绑定接线

### 6.1 ComfyUI history 解析扩展

现在 `comfyui/http.go` 的 history 解析只收图片，且结果拍平为 `[]OutputFile`。改为保留节点维度的结果：

- `Result.Outputs` 扩展为 `map[string]NodeOutput`（key 为节点 ID）或等价的带节点 ID 的数组；
- `NodeOutput` 至少包含 `images`、`text`（ComfyUI history 的 `text` 字段）、`files`；
- Mock 客户端同步调整（`Mock.Wait` 返回与绑定匹配的节点结构）。

### 6.2 JobPackage 携带输出绑定

`actuator.JobPackage` 增加 `Outputs []catalogdomain.OutputBinding`；`CaseSnapshot.BuildJobPackage` 从 Case 文档带入。Worker 不再依赖业务库读取绑定（保持 scheme-A job 包自包含）。

### 6.3 Worker 按绑定提取

`HandleDispatch` 成功后：

- 无输出绑定（旧数据）：回退现状，收集全部图片，保兼容；
- 有绑定：按 `bindings.outputs` 顺序逐个提取 `node_id` 对应产物的 `index` 项，落 Blob key `outputs/<taskID>/<key>.<ext>`，产物顺序与配置一致；
- 绑定节点不在结果中、或 index 越界：任务失败（`fail`），错误信息包含输出字段 key，便于定位。

### 6.4 通知

`channel/tg/adapter.go` 不再只发 `Outputs[0]`：按顺序发送全部输出（图片逐张发，文本输出作为消息文本 / 图片说明）。此改动独立于编辑器，属本 change 的一部分。

## 7. 前端技术要点

- 组件：在现有 `CaseForm` 基础上重组 `sections`，拆成 `WorkflowImportSection` / `InputFieldsSection` / `OutputFieldsSection` / `PreviewSection` / `AdvancedSection`；
- 节点别名表：常量 map（常见 `class_type` → 中文标签），未知节点回退原始类名；
- 类型推断：启发式规则（参数名与已知节点表），允许手改；
- 状态：`draft.bindings` / `draft.input_schema` 由表单字段实时推导，`workflow` 只在导入时写入；保存时统一 `buildPayload`；
- i18n：复用现有 `cases.*` keys，新增导入 / 节点选择 / 预览相关文案，保持 zh / en 成对；
- 现有 contract 测试模式（`*.contract.test.ts`）继续用于关键约束（如「列表面板没有 Select」「保存前校验存在」等）。

## 8. 错误处理

| 场景 | 表现 |
|---|---|
| 导入非 JSON / 非 ComfyUI / 结构损坏 | 红色横幅 + 人话 + 常见原因；不破坏已保存内容 |
| 字段名重复 / 必填未绑定 / 无输出 | 对应卡片标红，阻止保存 |
| 运行时绑定节点缺失 / index 越界 | 任务失败，错误含输出字段 key |
| 高级模式手改 JSON 非法 | 进入编辑时校验，非法则拒绝并标红 |

## 9. 测试策略

- **前端单测**：`parseWorkflow`（API / UI 格式 / 损坏输入）、`input_schema` 生成、`bindings` 推导；
- **前端 contract**：按现有模式断言「导入区存在 / 输入卡片含节点选择 / 高级模式默认只读」等；
- **后端单测**：`ValidateDocument` 图结构与绑定引用校验；history 解析含 text；Worker 按绑定提取 / 越界失败 / 无绑定回退；JobPackage 携带输出绑定；Mock 路径；
- **端到端冒烟**：mock Comfy 下「文本 + 图片输入 → 两个输出」的完整链路。

## 10. 风险

- **UI 格式转换版本差异**：ComfyUI 导出结构随版本变化；只承诺常见导出，失败给可读错误。
- **别名表覆盖不全**：未知节点显示原始类名，不阻塞配置。
- **text 输出语义**：ComfyUI history 的 text 字段格式需实测确认；先按「文本 blob + 通知文本」处理，后续可扩展。
