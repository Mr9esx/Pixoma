# Studio Run 连续性修复设计

## 目标与边界

修复 Studio 中间 Chat 的运行态、断线续接、审批、停止和服务重启语义。浏览器切换页面、刷新或关闭后重新进入同一 Session，只要服务端 Run 仍在运行，就接回同一个 Run、补齐离线期间的输出并继续流式显示。服务进程意外重启时，尚未开始执行的 Run 可以重新入队；已经开始执行且没有安全检查点的 Run 标为「执行中断」，不自动重放可能产生副作用的工具。等待批准的 Run 使用持久检查点，在批准后从中断位置续跑。

本设计只覆盖 Studio Chat 的运行机制，不调整资产、Flow 和其他后台页面的视觉结构。AI Elements 继续负责 Chat 展示，assistant-ui 继续承担 AG-UI Runtime 适配；Run 的真实状态不由这两个前端库决定。

## 根因与方案选择

现有实现同时使用数据库事件、`RunProgress` 快照和进程内 `EventHub` 历史作为补发来源。三者没有统一的提交边界。无序号文本增量无法去重，事件序号又通过读取最早 200 条事件计算。前端把连接结束当作 Run 结束，并在详情刷新时卸载活跃 Chat。审批和进程恢复还会从原始用户消息重新执行 Agent。

考虑过以下方案：

1. 保留三种来源并补游标判断。改动少，但无法从结构上保证快照与内存历史一致。
2. 持久化每个模型 token。续接语义简单，但写入频率和事件量过高。
3. **采用可重放的持久事件日志，合批保存高频文本增量。** 所有发送给客户端的输出先持久化并获得单调序号，再广播；`EventHub` 只通知新事件，不保存历史。此方案作为实施方案。

## 模块职责

| 模块 | 唯一职责 | 不承担 |
|---|---|---|
| `Run` 领域模型和协调服务 | 状态迁移、单 Session 活跃 Run 约束、取消与重启恢复决策 | WebSocket 连接状态 |
| 事件存储 | 原子分配 Run 内序号、写入事件、按序分页读取；重复序号报错 | 模型执行和 UI 快照拼接 |
| Agent 执行器 | 将模型、推理和工具输出合批提交；提交成功后通知订阅者 | 计算续接游标或替客户端缓存历史 |
| 审批服务与 Eino 适配器 | 保存审批记录和 Eino 检查点，批准后从检查点续跑 | 从原始问题重执行来模拟续跑 |
| AG-UI 适配器 | 校验身份及 Run 归属、顺序补发、订阅后续事件、映射协议 | 创建第二套运行状态或保存事件历史 |
| 前端 Run 连接控制器 | 维护当前 Run ID、最后确认序号、重连退避和状态对账 | 将 socket 关闭解释为终态 |
| Chat 视图 | 用 AI Elements 显示消息、推理、工具和审批操作 | 持有权威 Run 状态 |

## 持久事件与续接协议

- 每个 Run 的事件序号从 1 单调递增，由数据库事务或等价的原子操作分配。禁止通过 `ListEventsAfter(..., 0, 200)` 推断最大序号；`(run_id, sequence)` 冲突必须返回错误，不能静默忽略。
- 文本和推理增量按短时间窗口或字节阈值合批提交，在消息结束、工具调用、审批中断和 Run 终态前强制刷新。未提交的增量不向客户端广播。批次提交失败则停止该 Run，并保留可诊断错误；不得显示未持久化的内容。
- AG-UI attach 使用服务端 Run ID 和 `afterSequence`。订阅通知先建立，再从数据库分页读取 `sequence > afterSequence`；通知只触发下一次读取。客户端按序号去重，漏序时重新读取。空游标从当前 Run 的第一条事件补发，不跳到“当前最大序号”。
- 已结束的消息由 Session 历史读取；活跃 Run 的部分输出只从该 Run 的事件日志恢复。历史适配器不得把活跃 Run 的半截 assistant 消息再插入一次。
- `RunProgress` 可以继续作为 Session 详情的只读展示投影，但不再参与 AG-UI 补发或作为游标真相。投影丢失或落后不影响续接正确性。
- `EventHub` 不保存 Run 历史，通知发送不能阻塞 Agent 执行。订阅者断开只移除订阅，不改变 Run 状态。

## 状态、命令与前端生命周期

- Session 列表和详情读取同一套服务端 Run 状态。创建消息时提供幂等请求 ID；同一 Session 只允许一个 `queued`、`running` 或 `waiting_approval` Run。重复请求返回原 Run；另一条新请求在活跃 Run 存在时返回状态冲突。
- 详情后台刷新保留已挂载的 Chat 和连接。切换 Session 时可以卸载当前视图；返回后先读取 Run 状态，再 attach 原 Run。查询进行中显示现有内容及连接状态，不用骨架替换整个 Chat。
- WebSocket 意外断开时连接控制器带最后确认序号退避重连，并读取服务端 Run 状态。只有数据库终态或明确的审批中断才能将本轮标为结束或等待操作。网络错误显示可恢复状态，不把 Composer 误设为可发送。
- 审批是服务端命令。提交后以服务端响应和后续事件确认状态；重复提交按审批 ID 幂等处理。等待批准时显示可操作卡片，不触发“运行结束后刷新”导致的反复卸载。
- 「停止生成」调用服务端 Run 取消接口，收到确认后再更新 UI；仅关闭本地 socket 不是取消。取消与终态写入事件和 Run 状态应具有一致的提交顺序。
- assistant-ui Runtime 只用于当前 Chat 的交互和协议适配；AI Elements 组件及现有设计令牌保持不变，不新增解释性页面文案。

## 审批检查点与服务重启

审批工具在执行副作用前发出 Eino 可恢复中断。检查点使用持久存储，以 Run ID 关联审批记录和检查点；只有检查点保存成功后，Run 才可进入 `waiting_approval`。批准后调用 Eino `Resume`，而非再次调用 `Run`。工具侧保留以 Run ID 和稳定动作 ID 为键的幂等保护，防止重试或重复批准重复创建资产、Flow 节点或工作流任务。

启动恢复时分页处理全部待恢复 Run，不使用固定 200 条截断。`queued` Run 重新入队；有可用审批检查点的 `waiting_approval` Run 保持等待；无安全检查点的 `running` Run 转为 `failed`，错误码标识「执行中断」，并允许用户显式发起新一轮。不要把旧 Run 的部分输出伪装成已成功的回答。对于升级前已存在、缺少检查点的等待批准 Run，不自动重放工具；标记为需要重新发起并保留原审批与事件供排查。

## 兼容与迁移

已有事件和最终消息保留。新事件序号从数据库真实最大值之后分配；旧 `RunProgress` 只用于升级时读取与核对，不能让其水位越过未持久化事件。升级时对旧版活跃 Run 应执行明确的兼容检查：可安全续接的事件继续展示；无法从持久事件还原的未完成输出或缺失检查点的审批，显示执行中断并提供显式重试，不静默丢失或重复工具动作。迁移不得删除用户已有消息、资产和 Trace。

## 验收场景

1. 同一 Run 超过 200 条事件后仍能批准、续跑和完整补发，序号不冲突。
2. 文本、推理和工具输出中途切走、刷新或关闭浏览器；返回后无遗漏、重复或第二个 Run，并继续收到流式输出。
3. 详情刷新、窗口重新可见和网络恢复不卸载活跃 Chat；等待批准始终能看到并操作审批卡片。
4. WebSocket 意外关闭后后台 Run 继续执行，前端自动重连；只有服务端终态允许恢复发送。
5. 停止操作确实取消后台 Run；重复停止、重复批准和重复发送不会产生重复副作用。
6. 进程重启后 `queued` Run 恢复排队，已执行但无检查点的 Run 安全中断，等待批准且有检查点的 Run 可以续跑。
7. `EventHub` 慢订阅者不会阻塞 Agent；长 Run 的内存占用不随完整事件历史无限增长。

每个场景先补失败测试，再实施对应模块；验证包含 Go 单元与集成测试、前端连接状态测试、TypeScript 检查，以及真实页面的手动断线和审批流程。
