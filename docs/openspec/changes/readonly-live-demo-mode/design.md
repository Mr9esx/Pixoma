## Context

常规 Pixoma 启动链路会打开本地 `bootstrap.db`，读取已保存配置，迁移业务数据库，创建真实默认数据和后台 API。Live Demo 需要脱离这条持久化链路，并防止公开访客修改任何演示状态。

## Goals / Non-Goals

**Goals:**

- 提供独立于常规启动的 `-livedemo` 分支。
- 保证无 bootstrap 文件、业务数据库、Blob 写入和真实节点/频道连接。
- 固定登录账号为 `admin / 123456`，并在登录页提醒。
- 注入只存在于进程内存的演示数据。
- 对所有业务和管理写操作返回统一的只读错误。
- 隐藏设置菜单入口并拒绝设置、密码修改和注册接口。

**Non-Goals:**

- 不实现演示数据持久化、重启恢复或多访客数据隔离。
- 不在 Demo 模式下运行 Telegram、Edge Agent、真实 ComfyUI 或外部存储。
- 不改变常规模式的数据结构、权限模型或部署流程。

## Decisions

- 启动入口使用标准 `flag` 包解析 `-livedemo`；Go 会同时接受 `-livedemo` 与 `--livedemo`。
- 在 `run` 前进入独立的 `runLiveDemo` 分支，不复用 bootstrap 与 appboot 的落盘逻辑。
- 优先实现轻量内存仓储/适配器承载演示数据；现有内存实现可用时复用，不满足只读或领域形状时新增 Demo 专用实现。
- 通过 HTTP 中间件按方法和路径实施服务端只读与敏感接口拦截；前端隐藏入口只是体验优化，不能作为安全边界。
- 演示账号认证使用固定凭据校验和受内存控制的登录会话，避免创建 console account 或 bootstrap 管理员。
- 登录页和后台通过前端模式标识展示“Live Demo”提示并隐藏设置入口。

## Risks / Trade-offs

- [遗漏写路径导致状态可变] → 中间件默认拒绝非 `GET`/`HEAD`/`OPTIONS` 的后台 API，再为登录/登出维护白名单。
- [内存演示数据被并发修改] → 仓储内部加锁；服务端写拦截先于仓储方法执行。
- [设置或密码入口仍可被直接调用] → 服务端路径拦截返回统一错误，前端只隐藏入口。
- [演示数据显得不真实] → 使用稳定的中文示例数据、确定性时间戳和有统计关系的节点/任务/案例。
