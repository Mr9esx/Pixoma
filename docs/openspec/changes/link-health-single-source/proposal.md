## Why

消息平台、工作流、任务队列、计算节点构成一条配置链路，但绿黄没有主人：列表、详情、拓扑各自拿一截数据发明结论。某一跳坏了，只修「看见它的那一页」——例如工作流临时去看通道进程——挡不住下一处。队列仍不看上游平台，节点列表只看自己心跳，通道列表和详情用的信号还不一样。缺数据还当绿灯。要防的不是某一次通道故障，是这种「每页各算各的」结构。

## What Changes

- 健康与关联收成**唯一组装器**（控制面只读查询）。页面只渲染它的结论，MUST NOT 再调用各页自己的 `*References` / `listHealthTone` 发明绿黄。
- 规则是图上的**不变式**，不绑死某一种故障：某一跳不可用且没有别的活路，所有必须经过它才能跑通的资源都不得标绿。新增 hop 或新运行信号时，只扩展组装器与这条不变式测试，不给每个页面加 if。
- 组装器的输入必须是它能读到的配置与运行态。只活在某一个详情页缓存里的信号（例如只在打开通道详情才有的探测）不得当作全图真相。输入不齐 → pending，不得当绿。
- 四类资源的写模型仍分家：菜单、工作流、队列、节点继续各写各的。
- 列表圆点、详情「状态与关联」、工作台拓扑三处同色。
- 同步架构文档与架构图。

通道探测是否落库、适配器状态怎么读，都只是「让组装器看得见」的输入问题，不是本 change 的标题。

不拆成多个 change：只交接口而页面仍本地算，结构问题还在；只改前端纯函数，下次新信号仍会漏页。

## Capabilities

### New Capabilities

- `link-health-single-source`：配置链路唯一健康组装器、图与活路不变式、运行信号对组装器可见、页面只渲染。

### Modified Capabilities

- `admin-resource-pages`：工作流 / 消息平台 / 任务队列 / 计算节点的列表圆点、详情健康区块、工作台拓扑 MUST 使用组装器结论，MUST NOT 再各算一套绿黄。
- `admin-api-host`：控制面 MUST 挂载该只读查询，鉴权与既有管理 API 相同。

## Impact

- 后端：跨 BC 只读编排（不新建写侧限界上下文）+ 管理 HTTP 只读接口。现有通道/菜单/工作流/队列/节点的 CRUD 不合并。
- 前端：去掉各页重复的健康拼装；`link-health` / `config-topology` 只映射组装器 DTO。
- 测试：不变式（弄坏任一 hop、无活路 → 下游不得 ok），而不是「通道 error 则工作流 warn」这种点对点补丁测试当唯一验收。
- 文档：`docs/architecture/` 与架构图。
- 非目标：不合并四类写 API；不在图上编辑配置；不改 Task 执行/调度；Bot 不因链路黄拦截用户开跑；不做巡检推送；不把本次做成「把通道探测写进表」的专项。
