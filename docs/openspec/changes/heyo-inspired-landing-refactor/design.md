## Context

`web/landing` 是独立的 Vite 8 + React 19 + TypeScript + Tailwind CSS v4 SPA。现有 `LangLayout` 依次组装 Header、Hero、Features、Use Cases、CTA、Footer；`/cn` 与 `/en` 由 React Router 和 i18next 驱动；Bot、Case 目录、管理后台演示使用本地数据和按需加载，不依赖后端。

本次行为契约见 `specs/landing-page-experience/spec.md`。参考页是持续变化的外部站点，且其品牌素材和 livechat 内容不属于 Pixoma；因此复刻对象限定为当前页面的极简视觉语言、区块节奏、内容与演示交替方式、卡片组织、行动入口层级和响应式行为，不复制其商标、文案、媒体或实现代码。

## Goals / Non-Goals

**Goals:**

- 在现有 landing 工程内结构化重建页面，不另起应用或并入 `web/admin`。
- 让每个区块职责单一，页面顺序能从顶层布局直接读出。
- 复用现有三组交互演示及其本地状态，避免为了换视觉重写已验证的演示逻辑。
- 统一 landing 专用语义变量、区块容器、按钮和动效约束，使桌面与手机保持同一视觉语言。
- 保持双语、静态部署、键盘操作和减少动态效果支持。

**Non-Goals:**

- 不追求逐像素复制外部站点，也不引入其私有字体、图片、视频或源代码。
- 不新增真实产品功能、后端请求、登录、埋点、价格体系或第三方集成列表。
- 不改 `web/admin` 的设计令牌、组件或信息架构。
- 不新增截图或浏览器测试脚手架。

## Decisions

### 1. 采用顶层顺序组装，区块内部独立

`LangLayout` 只负责语言同步与页面区块排序，目标结构固定为：

```text
Header
HeroSection
FeatureShowcaseSection
CrossDeviceSection
AudienceSection
FaqSection
CTASection
Footer
```

每个区块自行读取 i18n 文案，并通过共用的 `SectionShell`、标题层级和容器宽度保持节奏一致。导航配置使用一份带锚点 ID 与文案 key 的常量，桌面导航、移动菜单和页尾从同一来源渲染，避免区块被删除后留下失效入口。

备选方案是继续把内容塞进现有四个大区块。该方案改动较小，但顶层结构无法对应参考页，也会让功能演示、适用人群和 FAQ 的职责混在一起，因此不采用。

### 2. 视觉上复刻节奏，不复制外部资产

参考页的可复用特征归纳为：克制的顶部导航、大字号首屏、明确主次 CTA、宽内容容器、交替的说明与产品界面、成组卡片、短标签引导区块、充足留白和轻量进入视口动效。实现时把这些特征映射到 Pixoma 内容，而不是复用 Heyo 的 DOM、CSS 或媒体文件。

全局样式继续集中在现有 landing 样式入口，颜色、字体、圆角、边框、背景和焦点环改用 landing 专用语义变量；组件只消费 `background`、`foreground`、`muted`、`border`、`primary` 等语义类。派生色使用 `color-mix(in oklch, …)`，不在组件中写裸色值或手写暗色覆盖。

备选方案是逐块硬复制参考页结构和样式。替换为 Pixoma 的文案与交互演示后，其固定尺寸容易失衡，也会把外部站点变化变成本项目维护负担，因此不采用。

### 3. 三组演示只换容器和编排

现有 `LazyBotChat`、`LazyCaseDir`、`LazyAdmin` 继续作为功能展示内容。新功能区采用 Heyo 式三列嵌套窗口：每张卡上半是演示、下半是说明，宽屏三列并可垂直错位，窄屏单列。Case 与后台接近视口后再装载；Hero 的 Bot 进入首屏包。

演示内部若存在与新语义变量冲突的外观，可做局部样式适配，但不改变交互步骤、mock 数据语义或组件公开接口。

备选方案是把演示改成静态截图或视频。它会丢失当前页面已经具备的可操作证据，也与确认范围冲突，因此不采用。

### 4. 新增区块只描述现有能力

- `CrossDeviceSection`：用 Telegram 移动端发起创作，用桌面 landing 演示对应的 Case、任务和节点管理；不宣称 Pixoma 有原生移动客户端。
- `AudienceSection`：覆盖个人创作者、小团队、多计算节点使用者，每张卡只写一个人群、一项主要收益和一个真实使用方式。
- `FaqSection`：回答安装方式、ComfyUI/算力归属、Telegram 使用、自托管与平台支持等现有能力问题，不承诺未实现能力。

中文文案遵守 `docs/voice-profile.md`：短句、直接、无感叹号和卖萌语气；英文保持相同信息量，不做逐字直译。

### 5. FAQ 优先使用可访问的现成组件

实现阶段先检查 `web/landing` 已有组件和 shadcn registry。若项目已有兼容 Accordion，则直接复用；否则用项目包管理器通过 shadcn CLI 添加，再按当前 alias 和 Tailwind v4 配置接入。FAQ 标题使用原生按钮语义，展开状态、内容关联、焦点环和键盘操作由组件契约提供。

不手写一套只有点击事件的折叠 `div`，避免遗漏 `aria-expanded`、`aria-controls` 和键盘行为。

### 6. 动效统一由可降级边界控制

继续使用现有 Motion 运行时和 `Reveal` 抽象。区块入场只动画 `opacity` 与 `transform`；FAQ 展开允许短时高度过渡；不增加持续抢注意力的循环动画。统一读取减少动态效果偏好，命中时关闭位移、循环和延迟，只保留立即显示与状态切换。

所有内容在动画启动前即具备正确文档顺序，动效失败或被关闭不影响阅读和操作。

### 7. 测试围绕行为契约，不做视觉快照

组件测试覆盖：

- 八个顶层区域的顺序，以及两个排除区域和入口不存在。
- `/cn`、`/en` 新词条完整，非法语言路径继续回退。
- 桌面导航、移动菜单、下载和自托管链接。
- FAQ 展开、收起、状态属性和键盘操作。
- 三组演示仍被装载且关键交互测试继续通过。
- 减少动态效果下内容直接可用。

样式与响应式通过结构、语义类、现有 lint 规则和人工代码审查约束，不引入图片快照。交付检查运行 landing 的 test、lint、build。

## Risks / Trade-offs

- [外部参考页继续变化，导致“复刻”基准漂移] → 以本设计记录的页面顺序和视觉特征为验收基准；不在实现中追随未确认的新区块。
- [现有演示视觉密度高，放入极简大区块后显得拥挤] → 演示逻辑不变，外层统一宽高、留白和裁切边界；窄屏允许自然增高，不缩到不可操作。
- [新增双语内容出现信息不对等] → i18n 测试逐项校验新 key，两种语言共享相同内容结构。
- [首屏和三组演示增加初始资源压力] → 保留惰性加载与轻量占位，只让首屏必要内容进入初始包。
- [精确视觉验证缺少截图测试] → 按项目约定使用代码结构、语义变量、响应式规则和人工浏览验收，不创建截图脚手架。

## Migration Plan

本次没有数据迁移。实现按“基础样式与共用组件 → 顶层结构 → 新区块与文案 → 演示重排 → 测试”的顺序落地，保持每一步都能本地渲染。

上线前构建 `web/landing` 静态产物并走现有部署路径。回滚时恢复本 change 修改的 landing 文件即可，不影响后台、API 或持久化数据。
